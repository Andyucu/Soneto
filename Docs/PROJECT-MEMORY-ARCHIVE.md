# Soneto — Project Memory

Living reference for anyone (human or agent) picking this project up cold. Update this file whenever a phase gate closes, a decision gets made, or an assumption from the plan docs gets invalidated. Keep `CHANGELOG.md` for chronological log entries; keep this file for the current-state snapshot.

## What this is

Push-to-talk dictation app. Hold a global hotkey, speak, release, punctuated text lands wherever focus is. 100% local inference, no cloud calls at runtime. English + Romanian via NVIDIA `parakeet-tdt-0.6b-v3` (int8, sherpa-onnx). Targets: Windows 11 first, Fedora KDE Wayland for parity, macOS deferred.

Full plans: `Docs/dictation-app-build-plan.md` (architecture/rationale), `Docs/soneto-implementation-plan-phase0-1.md` (execution plan, Phase 0 spikes + Phase 1 daemon).

## Key decisions locked in so far

- **English-first, Romanian accuracy deferred (2026-08-31):** the user has decided to proceed on the assumption Romanian accuracy is acceptable, without running S2's actual WER measurement right now, and to prioritize English. This is a deliberate scope decision, not a data-backed gate pass — S2 should be revisited before actually shipping/relying on Romanian dictation. Nothing in Phase 1 depends on this (ASR layer is language-agnostic), but the language-profile work in the build plan (§7.2) does, and shouldn't be built until S2 is actually run.

- **Stack:** C# / .NET 10 + Avalonia 11 (not Rust/Tauri — chosen for reuse of existing .NET skill investment, per `dictation-app-build-plan.md` §2).
- **Model:** `parakeet-tdt-0.6b-v3` only (v2 is English-only and was ruled out). No second ASR backend, no fallback model — this is a repeated hard constraint across both plan docs and every "opening prompt for Claude Code" template in them.
- **Capture mode default:** `OnDemand` (mic stream closed while idle, opens on key-down). `WarmIdle` is the documented fallback if S1b shows >150ms p95 stream-open latency or Bluetooth is in the mix.
- **Injection:** clipboard + synthetic paste, not per-character synthesis (diacritics + speed + Electron compatibility).
- **Decoding:** `greedy_search` by default; `modified_beam_search` hotword biasing is opt-in/experimental pending S6, due to a known NeMo TDT hallucination issue.
- **ASR thread count default:** `NumThreads=4`, not 8 as originally assumed in the plan — S1's thread sweep (2/4/8/16) found the knee at 4 on the dev machine (8 comparable, 16 worst and occasionally exceeded the 400ms bar). Seeds §1.6's `min(8, ProcessorCount-2)` default; re-verify on the actual target laptop before locking it in for Phase 1.
- **Capture mode default stays `OnDemand`** — confirmed by S1b: default mic p95=58ms, well under the 150ms bar. But `WarmIdle` is a documented near-term need, not just a theoretical fallback: this machine's paired Bluetooth headset failed to even start a capture stream under `OnDemand`, every trial.
- **Resampler tap count:** the plan's "32-tap" figure (§1.5) is wrong and was corrected by S1b — a 32-tap Blackman-windowed-sinc filter can't produce the required 7.8kHz→8kHz transition (its transition band would be ~8.25kHz wide). Real tap count needed: ~1200-1300 taps per phase for a single-stage design (confirmed again in item 4's product implementation: 1321 taps/phase at 48kHz, 1213 at 44.1kHz), or evaluate a multi-stage/cascaded halfband decimation approach for the exact 3:1 (48k→16k) case to cut compute (not built — item 4 uses the single-stage design). **The ~14ms zero-padded edge-taper artifact from S1b's spike is now resolved, not just unvalidated** — item 4's product resampler is stateful/streaming (maintains filter history across calls), so zero-padding only ever happens at the true start/end of an utterance stream, never at internal buffer boundaries. This was the correct fix, not a workaround: §1.5's own "accumulate into a growable list" wording implies per-buffer resampling calls throughout a stream, so a stateless design would have repeated the edge-taper artifact roughly every 10ms throughout every dictation.
- **Watchdog design correction for §1.4 edge case 3 ("key stuck down"):** S3 found the hook does NOT fully unhook when its callback is blocked (contrary to the plan's wording) — instead, the hook stays alive and dispatches normally afterward, but a key-up event that arrives during the block is silently and permanently dropped. A hook-liveness/heartbeat watchdog will miss this entirely, since the hook reports healthy the whole time. The `maxDurationMs` force-finalize timer on the DOWN event (already in §1.4's table) is confirmed necessary, not optional — this must be the actual defense, not just a nice-to-have.
- **§1.8 modifier sanitiser correction:** generic `VK_CONTROL` is ambiguous with the Right-Ctrl trigger key itself — reading it during/after a trigger press always shows "held" regardless of whether the user is also physically holding some other Ctrl key. §1.8's `SanitizeModifiers()` must read `VK_LCONTROL` specifically, not generic `VK_CONTROL`, confirmed via direct demonstration in S3.
- **§1.8 clipboard-restore correction (found by S4):** the plan's step-11 pseudocode has a TOCTOU race — the sequence-number check and the actual restore write were treated as separate operations. The real implementation must do the check-and-write as a single atomic critical section (open clipboard, check sequence number while still holding it open, write only if unchanged, close) — not open/check/close then separately open/write/close. Confirmed and fixed in S4's spike; carry the atomic pattern into Phase 1, not the plan's literal pseudocode structure.
- **Injection latency clarification (S4):** felt latency (paste actually landing) is ~35-47ms — fast. The literal "elapsed" number including the mandatory 150ms post-paste clipboard-restore-delay wait sits right at/slightly over the 200ms bar, but this isn't a real miss — that wait happens after the user already sees their text. Real issue: §4's latency budget (50-120ms for the whole clipboard+paste+restore stage) doesn't leave room for §1.10's default 150ms `clipboardRestoreDelayMs` — these two numbers in the plan are inconsistent with each other and need reconciling before Phase 1.
- **Recurring pattern worth watching for in every future item touching concurrency:** FIVE separate items now (S3's hotkey callback, S4's clipboard sequence-guard atomicity, item 4b's audio callback, item 4c's WarmIdle idle-close timer, item 6's heartbeat probe timer) have each had an explicit threading/concurrency constraint from the plan (or an obvious correctness requirement like "check-and-write must be atomic") violated in a first implementation attempt, and only caught by independent code review — never by the implementer's own manual testing, since these races are load/timing-dependent and don't reliably reproduce in a quick demo. Notably, item 6's hook-callback-thread discipline itself (the thing this pattern started with in S3) was implemented cleanly on the first pass — the bug this time was one level removed, in a *secondary* background timer (the heartbeat/watchdog mechanism), showing this failure class isn't confined to the "obvious" hot path once you're specifically watching for it there. Treat any new code with a background thread, a timer, a lock, or a "the plan says lock-free/atomic here" requirement as needing explicit review scrutiny for exactly this failure class, not just a "does it work" check — and don't stop scrutinizing just because the most obvious callback in an item turned out clean.
- **A sixth, related-but-distinct pattern, first caught in item 7 — a system-wide global hook can't tell "my own synthetic input" from "real user input" without an explicit signal, and code that assumes otherwise breaks deterministically, not rarely.** Item 6's hotkey hook observes ALL keyboard events system-wide, including synthetic `SendInput` calls from Soneto's own injection code (item 7) — so when the injector's paste chord happened to use the same virtual key as a configured trigger (`LeftControl`/`LeftShift`, both explicitly supported trigger aliases), the hook suppressed its own process's synthetic modifier keys and posted phantom hotkey events, breaking every single paste under that config. Not a race, not load-dependent — 100% reproducible, and easy to miss because the default trigger (`RightControl`) never collides with the paste chord's `Ctrl`/`Shift`. Fixed with the correct mechanism (`IsEventSimulated`/`LLKHF_INJECTED`) rather than a workaround. Worth checking for on every future item where a global hook/listener and a synthetic-input-generating component coexist: does anything the hook does depend on distinguishing its own process's synthetic events from real ones, and if so, is there an actual signal for that, or just an assumption?
- **Second recurring pattern, first caught in item 5 — reusing one config value for two conceptually different purposes can silently defeat a safety mechanism.** Item 5's whole-utterance VAD discard check ("the main defence against decoding empty audio") was implemented by reusing `MinSpeechMs` (Silero's per-segment filter) as the discard threshold too — which made the discard check structurally near-unreachable (total speech duration is, by construction, always ≥ any segment that survived the per-segment filter using the same number), not just a lower bar. It looked correct, built cleanly, and passed a demo — the bug only showed up when a reviewer asked "can this check actually ever fire, given how the two numbers interact?" Fixed with a genuinely separate config field (`VadConfig.MinUtteranceMs`). Worth checking for this shape of bug whenever a single config value gets pressed into service for two different comparisons/gates in the same component — ask whether the two purposes can actually diverge, or whether one silently subsumes the other.
- **Operational caution for future spikes/testing:** automated multi-app UI injection testing against a live, in-use desktop is riskier than it looks — S4's automated app-launch matrix had a foreground-window-detection bug that caused several "successful" injection results to actually land on stale leftover windows instead of the intended real app (in this case, a desktop with a real signed-in Teams work account and real Outlook/Word open). No real content was affected, but future per-app testing should use a human-supervised one-at-a-time countdown mode, not a batched automated launcher, especially on a machine with real accounts logged in.
