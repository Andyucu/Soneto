# Soneto — Phase 3 Implementation Plan: Avalonia Shell

Companion to `soneto-implementation-plan-phase0-1.md` (Phase 0 spikes + Phase 1 headless daemon) and `soneto-implementation-plan-phase2.md` (Phase 2 dictionary engine), both done as of 2026-09-02 — see `Docs/PROJECT-MEMORY.md` for current status. This doc does for Phase 3 what those did for their phases: a real spec with exact shapes, an explicit architecture decision the build plan itself doesn't make, and a work-item breakdown with pass criteria, written before implementation.

Source material: `Docs/dictation-app-build-plan.md` §3 ("Architecture"), §6.2's observability paragraph, §8 ("Data & privacy"), and §10's Phase 3 summary line. Read that doc directly if this one and it ever disagree — this is the detailed execution plan, that's the design rationale.

## 3.1 Definition of done

Per the build plan's own phase summary: **"Tray icon, main window, searchable history (FTS5) with per-entry copy and rule-fired diff, live level meter, settings (hotkey, model, threads, language profile bindings), permissions doctor. Define design tokens first... and have every view pull from them."** Plus one carried-forward item the Phase 2 plan explicitly deferred here by name: **"Phase 3 builds the Avalonia [dictionary] editor"** (`soneto-implementation-plan-phase2.md` §2.1).

Acceptance, concretely: a human can launch `Soneto.App`, see a tray icon, hold the configured hotkey anywhere on the desktop, see a live level meter while speaking, have punctuated text land at the cursor exactly as it does today via `Soneto.Daemon`, then open the main window and see that utterance in a searchable History list with a raw-vs-final diff showing which dictionary rules fired, edit a dictionary entry in a real UI (not by hand in `dictionary.json`) and see it take effect on the next utterance, rebind the hotkey and adjust ASR/audio/injection settings from a Settings page, and run a Permissions Doctor page that reports real red/green status for mic access, hook health, input synthesis, clipboard access, and model file presence/hash.

**Explicitly out of scope for Phase 3** (per the build plan's own phase boundaries — don't scope-creep into these):
- **macOS anything.** No `.app` bundle, no `CGEventTap`, no Accessibility-permission flow. Deferred to Phase 4 per the build plan's own phasing.
- **Linux Wayland productionization** (`ydotoold`/`uinput` setup UX, the `setup-linux.sh` script, a dedicated Wayland permissions flow). Item 11's Phase 1 code already runs best-effort on Wayland; hardening that experience is explicitly Phase 4 scope. The Permissions Doctor (§3.14) still reports what it can on Linux today — it just doesn't gain new Linux-specific remediation UX this phase.
- **Per-app profile selection** (§6.5 — terminal/Teams/IDE profiles). Still Phase 4, per Phase 2's own scope note; this phase does not add a "which app is focused" mechanism.
- **The n-gram language-detection classifier** (§7.2 item 1 — "detect the output language post-hoc"). This does not exist yet anywhere in the codebase. The build plan's shell description mentions a "detected language chip" on the recording HUD, but that chip has a real, unbuilt dependency — building the classifier just to paint one HUD glyph would be scope creep into language-profiling work this doc explicitly does not own. **Decision: the HUD ships without a language chip this phase**; see §3.10 for exactly what it does ship. The chip is Phase 4's to add once the classifier exists.
- **The optional LLM polish pass** (§7.3). Off by default, not scoped here at all.
- **Dictionary import/export, first-run wizard, auto-start on login.** These are the build plan's own Phase 5 ("Polish") items, not Phase 3.
- **Distribution** (installers, RPM/Flatpak, notarised DMG, CI matrix builds). Phase 6.

## 3.2 The one thing this phase does that Phase 2 explicitly could not: touch `SessionController`

Phase 2's §1.16/§2.2 made "if this needs a `SessionController` change, stop and reconsider" a hard rule, because Phase 2 was supposed to be purely additive `IPostProcessor` plumbing. **Phase 3 has no equivalent constraint** — a UI needs to observe what the daemon is doing (recording state, live audio level, and — new in this phase — a completed utterance's raw/final text and which rules fired on it), and `SessionController` today exposes only `StateChanged` (Recording/Idle/Faulted transitions) and `IAudioCapture.LevelChanged` (already built, §3.10). There is no event carrying `{raw text, final text, AppliedRule[], timestamps}` for a completed dictation, and there needs to be one for History (§3.7) to have anything to persist. This is a deliberate, scoped, single-purpose extension to `SessionController` — not an invitation to restructure it. Treat every other item in this phase as UI/persistence work layered on top of the existing pipeline, exactly the way Phase 2's four processors were layered onto `PostProcessorChain`.

## 3.3 Architecture decision: `Soneto.App` becomes the real product; `Soneto.Daemon` stays as a headless harness

The build plan's own architecture diagram (`dictation-app-build-plan.md` §3) draws `Soneto.App` (Avalonia) as the single process hosting the shell AND `Soneto.Core`'s pipeline in-process — there is no separate always-running daemon process with a UI talking to it over IPC anywhere in the plan. But Phase 1/2's real work landed in `Soneto.Daemon` (a console/service host with no UI), which already does the full `BuildAndStartSessionControllerAsync` composition (model resolution, capture, VAD, post-processor chain, injection, config/dictionary hot-reload — see `Docs/PROJECT-MEMORY.md`'s item 9/10 entries).

Building IPC between a headless daemon and a separate UI process is real, unscoped, un-asked-for complexity — nothing in the build plan calls for two processes, and adding one now would mean designing and securing a local IPC channel, a job neither plan doc ever describes. **Decision: `Soneto.App` absorbs `Soneto.Daemon`'s real composition logic in-process, becoming the shipped end-user executable — a single process, exactly as the build plan's diagram shows.** Concretely:
- `Soneto.Daemon`'s `BuildAndStartSessionControllerAsync`/`BuildPostProcessors`/config-and-dictionary-service wiring gets extracted into a shared composition helper so `Soneto.App` and `Soneto.Daemon` both call the SAME composition code rather than forking it. **Decided in item 0, not deferred to item 4 as originally sketched here:** a new top-level `src/Soneto.Composition/` class library (`Soneto.Composition.DaemonComposition`, a static class with `ILoggerFactory`-in/instances-out methods, no DI-container registration — chosen specifically because a future Avalonia composition root won't have `Soneto.Daemon`'s `Microsoft.Extensions.Hosting` container), NOT a folder nested under `Soneto.App` (§3.4's diagram below is stale on this specific point, kept for the original section-numbering but superseded by this note). Do not duplicate the ~40 lines of "resolve model, build transcriber, build capture, build chain, build controller, start it" logic a second time inside `Soneto.App` when item 4 lands — that is exactly the kind of drift this project's own established discipline (shared `BuildAndStartSessionControllerAsync`, already written once to serve both the Windows and Linux branches of `Main`) has avoided elsewhere.
- `Soneto.Daemon` is **not deleted**. It stays as a genuinely useful headless harness: CI-friendly (no window server needed), the natural home for `--transcribe`/`--record`/`--watch-hotkey`/`--inject` and any future scripted verification, and a safety net if `Soneto.App`'s UI layer ever needs to be debugged independently of the pipeline. Document this explicitly in `Docs/ARCHITECTURE.md` so a future reader doesn't wonder why there are two entry points.
- `Soneto.App` is a `WinExe`-style Avalonia project (no console window on Windows), multi-targeted `net10.0;net10.0-windows` the same way `Soneto.Daemon` is, with the same conditional `Soneto.Platform.Windows` reference pattern.

`Soneto.Core/History/` is deliberately in `Soneto.Core`, not `Soneto.App` — `Microsoft.Data.Sqlite` is a pure managed/native-P-Invoke package with no Windows- or Linux-specific API surface (unlike `IHotkeySource`/`ITextInjector`), so `IHistoryStore` can and should follow the same "lives in Core, no platform reference" rule every other cross-cutting service (`ConfigService`, `DictionaryService`) already follows. This also means `IHistoryStore` is testable in `Soneto.Core.Tests` with a real temp-file SQLite database, no UI project needed to exercise it.

Tests: `tests/Soneto.Core.Tests/History/` for `IHistoryStore`. Avalonia UI logic is tested via **ViewModel unit tests only** (see §3.16) — there is no `Soneto.App.Tests` UI-automation project in this phase.

## 3.5 History persistence (`Soneto.Core/History/`)

### Data model

```csharp
public sealed record HistoryEntry(
    long Id,                              // SQLite rowid
    DateTimeOffset Timestamp,
    string RawText,                       // pre-post-processing ASR output
    string FinalText,                     // post-chain, what was actually injected
    IReadOnlyList<AppliedRule> RulesFired, // serialized as JSON in the row, deserialized on read
    TimeSpan RecordingDuration,
    TimeSpan ProcessingLatency,            // key-up -> injected, the plan's own §4 budget metric
    bool WasInjected);                     // false if injection failed/was skipped (still worth keeping in history)
```

`AppliedRule` is already a public `Soneto.Core.Abstractions` record (`Processor`, `Rule`, `From`, `To` — populated for real since Phase 2 item 4). Store it as a JSON array column rather than a normalized child table — there is no query this phase needs that filters/joins on individual rule firings (only "show me this entry's diff"), so normalizing it now would be schema complexity with no corresponding requirement. Revisit only if a future phase needs "show me every utterance where rule X fired."

### SQLite schema, with FTS5

```sql
CREATE TABLE history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp_utc TEXT NOT NULL,          -- ISO-8601, sortable as text
    raw_text TEXT NOT NULL,
    final_text TEXT NOT NULL,
    rules_fired_json TEXT NOT NULL,       -- '[]' if none
    recording_duration_ms INTEGER NOT NULL,
    processing_latency_ms INTEGER NOT NULL,
    was_injected INTEGER NOT NULL         -- 0/1
);

CREATE VIRTUAL TABLE history_fts USING fts5(
    final_text,
    content='history',
    content_rowid='id'
);

-- Triggers to keep history_fts in sync with history (insert/update/delete) --
-- standard SQLite FTS5 external-content-table pattern; write these explicitly,
-- don't rely on a library to generate them.
```

**Verify FTS5 is actually available before building on top of it** (item 1's first task, not asserted here as fact): `Microsoft.Data.Sqlite`'s bundled `SQLitePCLRaw.bundle_e_sqlite3` native library is built with FTS5 enabled in the versions this project would pull in, but confirm this directly — `PRAGMA compile_options;` should list `ENABLE_FTS5`, or a trial `CREATE VIRTUAL TABLE ... USING fts5(...)` should simply not throw. If it's NOT available for any reason, fall back to a `LIKE '%term%'` search over `final_text` for this phase (slower, no ranking, but functionally adequate for a personal history of a few thousand rows) and file it as a documented, honest limitation rather than silently blocking the whole phase on a packaging issue — mirroring this project's established "verify the plan's stated primitive actually exists before depending on it" discipline (S1's `OfflineRecognizerConfig` shape check, item 9/10's `SeedDictionary`/`DictionaryDocument` round-trip proofs).

### `IHistoryStore` contract

```csharp
public interface IHistoryStore : IAsyncDisposable
{
    Task<long> AppendAsync(HistoryEntry entry, CancellationToken ct = default);
    Task<IReadOnlyList<HistoryEntry>> SearchAsync(string? query, int limit, int offset, CancellationToken ct = default);
    Task<int> PurgeOlderThanAsync(TimeSpan age, CancellationToken ct = default);  // retention sweep, §3.15
    Task PanicWipeAsync(CancellationToken ct = default);                          // deletes ALL history rows, §3.15
}
```

`AppendAsync` runs on the hot path (right after every completed dictation — see §3.7) and **must never throw and must never block the injection path on a slow disk**. Mirror `ConfigService`/`DictionaryService`'s "never throws" discipline: catch `SqliteException`/`IOException` around the actual write, log, and drop the entry rather than propagate — losing one history row is a much smaller problem than a hung or crashed dictation session. Call `AppendAsync` as fire-and-forget from `SessionController`'s completion path (§3.7), not awaited inline before the text is already injected — history persistence must never add latency to the plan's own §4 budget.

## 3.6 `SessionController` extension: `DictationCompleted`

Add one new event, additive to the existing `StateChanged`:

```csharp
public sealed record DictationCompletedEventArgs(
    string RawText, string FinalText, IReadOnlyList<AppliedRule> RulesFired,
    TimeSpan RecordingDuration, TimeSpan ProcessingLatency, bool WasInjected);

public event EventHandler<DictationCompletedEventArgs>? DictationCompleted;
```

Raised exactly once per completed recording (success or a handled failure that still produced text), from the same place `SessionController` already knows the final post-chain text and whether injection succeeded — read the existing state-machine code before wiring this in; do not add a second code path that could raise `DictationCompleted` out of step with what was actually injected. This is the ONE `SessionController` change this whole phase makes (per §3.2) — keep the diff to this event and its single raise-site, resist the urge to also refactor anything else in that file while you're in there.

`Soneto.App`'s composition helper (§3.3) subscribes to this event and calls `historyStore.AppendAsync` (fire-and-forget, per §3.5) and forwards it to the History view's live-updating list (§3.11) if the main window is open.

## 3.7 Design tokens

Per the build plan's own explicit advice ("define design tokens first... and have every view pull from them" — correct, and worth following literally): before building any view, create `Soneto.App/Styles/` with:
- `Colors.axaml` — a semantic palette (`Background`, `Surface`, `TextPrimary`, `TextSecondary`, `Accent`, `Success`/`Warning`/`Danger` for the Permissions Doctor's red/green, `Border`) with light AND dark variants from the start (Avalonia's `ThemeVariant` resource dictionaries), not a single hardcoded palette retrofitted for dark mode later.
- `Typography.axaml` — a small type scale (e.g. `Display`/`Title`/`Body`/`Caption`), one font family, consistent line-heights.
- `Spacing.axaml` — a spacing scale (4/8/12/16/24/32px, named not magic-numbered) used for every margin/padding in every view.
- `Elevation.axaml` — corner radius and shadow tokens for cards/panels (the History list's entries, the Permissions Doctor's status cards).
- `Motion.axaml` — transition durations/easings (window open, tray-to-window restore, the recording HUD's fade-in/out) — a small, consistent set, not per-view ad-hoc durations.

Every subsequent view item in this build order pulls colors/spacing/type from these files via `{DynamicResource ...}` bindings — never a hardcoded hex color or magic-number margin in a view's XAML. Verify this discipline holds with a quick "kitchen sink" test view during item 3 (a scratch page rendering every token) rather than trusting it by convention alone.

## 3.8 Shell: tray icon + main window

- **Tray icon**, always present while the app runs: left-click restores/focuses the main window, right-click menu has at minimum "Open Soneto", "Pause dictation" (toggle — stops the hotkey from starting new recordings without killing the process, useful during screen-shares), and "Quit". Closing the main window's `X` button minimizes to tray rather than exiting the process (standard tray-app convention) — make this configurable in Settings (§3.13), don't hardcode it as the only behavior, since some users will want `X` to actually quit.
- **Main window**: a simple sidebar/nav-rail shell (History / Dictionary / Settings / Permissions, in that order — History first since it's the most-used surface day to day) with each destination a separate `UserControl`+`ViewModel` pair, not one giant view. No deep navigation stack needed — four flat top-level pages is the right amount of structure for this app's actual scope.

## 3.9 Recording HUD + live level meter

A small, always-on-top, borderless window that appears the moment `SessionController.StateChanged` transitions to `Recording` and disappears on the transition back to `Idle`/`Faulted`. Contents, per §3.1's scope decision (no language chip — §3.1):
- A live level meter, subscribed directly to the ALREADY-BUILT `IAudioCapture.LevelChanged` event (`AudioLevelEventArgs.Dbfs`, firing at ~20Hz per that class's own doc comment) — this item is pure UI wiring onto an existing signal, not new audio-side work.
- An elapsed-time counter since recording start.
- Positioned near the cursor or a fixed screen corner (implementer's call, document the choice) — must not steal focus from whatever app the user is dictating into, a hard requirement given the whole point of push-to-talk is not disrupting the focused app.

## 3.10 History view

- A scrollable list of `HistoryEntry` rows (newest first), each showing a truncated `FinalText` preview, timestamp, and a copy-to-clipboard button.
- A search box wired to `IHistoryStore.SearchAsync`, debounced (mirror the 500ms-ish debounce convention already established for config/dictionary file-watching, though this is keystroke debouncing, a different mechanism — a simple `DispatcherTimer`-based debounce is enough, no need to reuse `ConfigService`'s `System.Threading.Timer` pattern verbatim since there's no file-watcher/dispose-race shape here to mirror).
- Selecting an entry opens a **diff view**: `RawText` vs `FinalText`, with each `AppliedRule` highlighted at its `From`/`To` span in the diff (this is the build plan's own explicit observability requirement from §6.2 — "the history view shows a diff... without this you cannot tell whether the dictionary is doing anything"). A simple side-by-side or inline-highlight rendering is enough; this does not need a general-purpose diff algorithm since `AppliedRule` already carries the exact spans that changed — use that structured data directly rather than running a text-diff library over `RawText`/`FinalText` and trying to reverse-engineer what changed.

## 3.11 Dictionary editor — the Phase 2 deferral this phase closes

Per `soneto-implementation-plan-phase2.md` §2.1's own words: *"Any UI. `dictionary.json` is hand-edited. Phase 3 builds the Avalonia editor."* This item builds that editor:
- A list of all `DictionaryEntry`s (from `DictionaryService.Current.Entries`), grouped or filterable by the five entry types, each with an enable/disable toggle.
- Add/edit/delete forms for each of the five types (`VocabularyTerm`/`CorrectionPair`/`RegexRule`/`SpokenCommand` — `PerAppOverride` gets a form too since the schema already supports it, even though nothing consumes it yet per Phase 2's own §2.9 deferral; label it clearly as "not yet active" in the UI so a user doesn't wonder why a per-app override they configured has no effect).
- **The editor writes to `dictionary.json` directly and relies on `DictionaryService`'s ALREADY-BUILT `FileSystemWatcher`+debounce to pick the change up** — worth calling out explicitly as a deliberate reuse, not new plumbing: there is no need to build a second "tell the running service about this edit" code path, since item 9's hot-reload mechanism was built exactly to handle a `dictionary.json` change from any source, including this UI's own writes. The one thing this item DOES need to add: surface `DictionaryService`'s validation feedback (a rejected entry, a duplicate-Id whole-file rejection, a `DictionaryCollisionWarnings` advisory) back into the UI as a visible error/warning, not just a log line a user will never see — this may need a small additive change to `IDictionaryService` (e.g. exposing the last load's `RejectedEntries` and any collision warnings as UI-observable state) — keep this change as narrowly scoped as `DictionaryConfig`'s existing shape allows; don't restructure `DictionaryService` itself.
- Given the still-live "no live rebuild into a running `SessionController`" limitation from item 10 (`Docs/PROJECT-MEMORY.md`), the editor must show a clear, honest "changes will apply on next restart" notice — do not let the UI imply an edit is live in the current session when it isn't.

## 3.12 Settings

One page, sectioned (not a single giant form):
- **Hotkey** — a "click to record a key" control rebinding `HotkeyConfig.Key`/`Suppress`, writing back to `config.json` (same reuse-the-existing-hot-reload principle as §3.11's dictionary editor — `ConfigService`'s watcher already exists).
- **ASR** — model directory override, thread count, decoding method (surfacing `AsrConfig`'s existing fields; no new ASR functionality).
- **Audio** — capture mode, device selection, VAD thresholds (surfacing `AudioConfig`/`VadConfig`).
- **Injection** — method, paste chord, clipboard policy (surfacing `InjectionConfig`).
- **Language profile binding** — the build plan's §7.2 item 2, explicitly deferred out of Phase 2 as needing a `SessionController` change ("bind a second hotkey as a profile hint... needs `SessionController` changes... explicitly out of Phase 2's scope"). This phase is the first one where touching `SessionController` for a UI-driven feature is in scope (§3.2), so build the second-trigger-binding mechanism here: a second configurable hotkey that, when used instead of the primary trigger, tags the resulting `DictationCompletedEventArgs`/history entry with a language-profile hint. **Do not build the profile-driven dictionary/grammar SWITCHING itself in this item** — that consumes the hint to select a different rule set, which depends on Phase 4's per-app-profile-style selection mechanism (§6.5) that doesn't exist yet; this item only builds the second-hotkey CAPTURE and lets it flow through as inert metadata for now. Document this partial-completion explicitly, the same honest-gap style Phase 1 used for items 11/12.

## 3.13 Permissions doctor

A page that actively tests, not just describes, each capability from §5.3's list and shows red/green:
- Mic access (attempt a very short capture-stream open/close via the existing `IAudioCapture`, don't just check an OS permission flag that may not reflect actual usability).
- Global hook active (query `IHotkeySource`'s current health/fault state — `SessionController`'s existing hook-fault-detection plumbing from Phase 1 already tracks this).
- Can synthesize input (a real, harmless self-test — e.g. a synthetic keypress into a throwaway invisible control inside `Soneto.App` itself, never into an arbitrary foreground window; **do not repeat this project's documented live-desktop near-miss pattern** — see `Docs/PROJECT-MEMORY.md`'s "live-desktop testing caution" entries from S4/item 7b. This self-test must target a window this process owns, never `GetForegroundWindow()`/whatever is currently focused).
- Clipboard read/write (round-trip a throwaway marker value through the real clipboard API and read it back).
- Model files present & hashed (reuse `ModelManager`'s existing SHA-256 verification path directly — no new hashing logic).
- On Linux: `/dev/uinput` writable, `ydotoold` running — best-effort checks only this phase (report red/green, but do not build the remediation/setup-script UX that's explicitly Phase 4 scope per §3.1).

## 3.14 Data & privacy controls

Per §8: audio is never written to disk by default — this phase adds the explicit, opt-in "keep last N clips for debugging" toggle in Settings (off by default), wired so enabling it captures raw WAV alongside a history entry's `Id` for correlation, with its own separate auto-purge (distinct from the text-history retention below, since audio clips are far larger and more sensitive). History itself gets:
- An "auto-delete history after N days" setting, enforced by a background sweep calling `IHistoryStore.PurgeOlderThanAsync` on a timer (daily is enough — this doesn't need FileSystemWatcher-grade responsiveness).
- A "panic wipe" button (with a real confirmation dialog, not a single accidental-click delete) calling `PanicWipeAsync`.

## 3.15 Testing

Avalonia UI code is genuinely harder to unit-test than the pure-logic code every prior phase dealt with, and this project has a standing, explicit caution (`Docs/PROJECT-MEMORY.md`, "live-desktop testing caution") against automated tests that drive real synthetic input against a shared, in-use desktop. Given both facts:

- **ViewModel logic is unit-tested directly**, with no `Avalonia.Headless`/UI-automation harness needed for most of it — a `HistoryViewModel`'s search-debounce/paging logic, a `DictionaryEditorViewModel`'s validation-forwarding, a `SettingsViewModel`'s config round-tripping, and a `PermissionsDoctorViewModel`'s red/green-state aggregation are all plain C# objects that take fakes/mocks for `IHistoryStore`/`IDictionaryService`/`IConfigService` and can be tested exactly like `Soneto.Core.Tests`' existing style.
- **`IHistoryStore`/SQLite/FTS5 is tested for real**, against real temp-file databases (mirroring how `ConfigService`/`DictionaryService` tests use real temp files, not mocked file I/O) — this is pure-logic-adjacent code with no UI/live-desktop risk at all.
- **XAML/visual rendering and actual tray/window/hotkey behavior is verified MANUALLY by a human**, one feature at a time, the same way Phase 1's items 6/7's hardware-dependent claims were flagged as needing human verification rather than agent-automated. Do not attempt to script real global-hotkey-into-real-foreground-app UI tests the way S4's original app-launcher matrix did — that is exactly the pattern this project's memory warns against. If a UI behavior needs verifying against real focus/foreground state, ask a human to do it, one app at a time, the same caution already established for injection testing.
- Do not build a `Soneto.App.Tests` UI-automation project in this phase — if end-to-end UI automation is ever wanted, that's a deliberate future decision requiring its own risk discussion, not a default this plan adopts.

**Superseded by item 6 (2026-09-02):** item 6's own work-item instructions explicitly called for a `Soneto.App.Tests` project — the first real `HistoryViewModel` is exactly the kind of pure, ViewModel-level logic this section's own first bullet already says should be unit-tested "exactly like `Soneto.Core.Tests`' existing style." The line above is corrected, not silently overridden: `tests/Soneto.App.Tests/` now exists, but it is NOT the UI-automation project this bullet was warning against — it contains zero `Avalonia.Headless`/simulated-input/rendering code, only plain xunit tests of `HistoryViewModel` against a `FakeHistoryStore` in-memory test double. The distinction this bullet draws (ViewModel-level unit tests are fine and expected; driving real synthetic input against a shared live desktop is not) still holds exactly as written — only the "don't stand up a `Soneto.App.Tests` PROJECT at all" framing was too broad, since nothing about this section's own philosophy actually requires ViewModel tests to live inside `Soneto.Core.Tests`.

## 3.16 Build order

Following the same "one work item per session, each with a real demo/test" discipline the prior two phases established.

| # | Item | Done when |
|---|---|---|
| 0 | Extract `Soneto.Daemon`'s composition logic (model/capture/VAD/chain/controller wiring) into a shared helper both `Soneto.Daemon` and the not-yet-created `Soneto.App` will call (§3.3); no behavior change to `Soneto.Daemon` itself | ✅ Done (2026-09-02). New top-level `src/Soneto.Composition/` class library (`DaemonComposition`, a static class with `ILoggerFactory`-in/instances-out methods — deliberately no DI-container registration, since a future Avalonia composition root won't have `Soneto.Daemon`'s `Microsoft.Extensions.Hosting` container). `Soneto.Daemon/Program.cs`'s real daemon-startup path now calls `DaemonComposition.CreateConfigService`/`CreateDictionaryService`/`LoadAndStartWatchingConfigAsync`/`LoadAndStartWatchingDictionaryAsync`/`CreatePlatformHotkeySourceAndTextInjector`/`BuildAndStartSessionControllerAsync`/`BuildPostProcessors` end to end, with zero remaining duplication (confirmed: the CLI-harness-only commands — `--transcribe`/`--record`/etc. — legitimately keep their own standalone construction, since they never shared the daemon's real composition path even before this refactor).
